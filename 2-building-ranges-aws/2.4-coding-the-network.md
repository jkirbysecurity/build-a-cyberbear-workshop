# 2.4 - Coding the Network

### Objectives

The objectives of this lesson are to build and configure the **network resources** for your CyberBear Range using Terraform.

- VPC
- CIDR Blocks
- AWS Region and Availability Zone
- Subnets
- Internet Gateway
- Route Tables


## Challenges

In AWS, a VPC is a Virtual Private Cloud.  Think of this as your very own private network in AWS.  There are several things we need to setup and configure for our cloud network before we can add our EC2 Instances to the range.

For our CyberBear Range, we will start by setting some of the initial variables you will need for creating the VPC. You can hardcode everything, but that is not a good use of time and energy.  It is better to create variables for values that will be reused across many resources.  That way if you need to make a change at any time, you only need to change the value in one place.

- CIDR block (IP address block) for your VPC
- Region and Availability Zones you want to work in  
- Subnet CIDR block

Once you have set some of the initial variables, you can add and configure the VPC and subnet resources for your range.

Let's take a look at how this is done in Terraform.

:warning: **WARNING:** Copy/pasting code blocks from this workbook tends to add extra spaces at the beginning of lines.  This **DOES NOT** impact the running of the code.  Also, just run `terraform fmt` to beautify your code, and all will be good again in the world.

### Challenge 1: Set Your variables -- VPC CIDR Block, Region, Availability Zones, and a Project Name

1. Copy the code blocks for the following **variables** and paste them into the **VARIABLES** section of your CyberBear Range Template.  

    - **Notice** the default variable configurations being set

          # Set the default CIDR block you want to work in 
          variable "cidr" {
            description = "The base CIDR block used for the VPC and all subnets" # Documents purpose
            default     = "10.0.0.0/16" # Sets default value
            type        = string        # Data type
            validation { # Validation conditions and error message if validation fails
              condition     = contains(["16", "21"], split("/", var.cidr)[1])
              error_message = "Only /16 or /21 CIDR notation is accepted."
            }
          }

          # Set the default region you want to work in
          variable "region" {
            description = "The AWS region to use for deployment"
            default     = "us-east-2"
            type        = string
          }

          # Set the default availability zones
            variable "availability_zones" {
            description = "Availability zones to use"
            type        = list(string)
            default     = ["us-east-2a", "us-east-2b"]
          }

          # Give your project a name
          variable "project" {
            description = "Project identifier for resource naming"
            type        = string
            default     = "cyberbear-range"
          }


### Challenge 2: Set the CIDR Block Local Variable for Your Subnets

1. Copy the **locals** code block and add to the **LOCAL VARIABLES** section of your CyberBear range.  For this piece, we are adding a naming prefix for our resources and the CIDR blocks we want to use for our range subnets.  

    - **Notice** we are adding a `name_prefix` in our locals using the "project" variable.  This means we want to use the project variable to prefix the names of our resources.  This is a good way to codify a naming convention for your projects.

          locals {
            name_prefix = "${var.project}"

            # Set the CIDR block for the server subnet
            public_sub_cidr_block  = "10.0.1.0/24"
            private_sub_cidr_block = "10.0.2.0/24"

          }


### Challenge 3: Create Your CyberBear Range VPC

1. Visit the following Terraform resource documentation for building AWS VPCs, review the docs and learn how to use the resources.

    - [Resource: aws_vpc](https://registry.terraform.io/providers/hashicorp/aws/latest/docs/resources/vpc.html)
    - Some of the sections worth reviewing include:
        - **Example Usage** -- Demonstrates a general "how-to" use this resource
        - **Argument Reference** -- These are the resource attributes and configurations 
        - **Attribute Reference** -- These are the attributes that are exported after creation of this resource.  Attributes can be referenced as **outputs** and/or as **inputs** for other resources.
        - **Import** -- This is how you would **import** an existing resource of this type

2. Copy the **VPC** resource code block and paste it into the **NETWORK** section of your CyberBear Range.

        # Creates a VPC (isolated network) with a specific IP range
        resource "aws_vpc" "vpc" {
          #cidr_block           =  # IP address range for the VPC
          enable_dns_support   = true     # Enables internal DNS resolution
          enable_dns_hostnames = true     # Enables DNS hostnames for EC2 instances

          tags = {
            Name = "${local.name_prefix}-vpc"
          }
        }

3. Set the `cidr_block` input for the VPC resource

    - Remember, we previously set the CIDR block variable.  For the resource that we are using to build our range VPC, all we have to do is use the variable we previously set by having the `cidr_block` input = `var.cidr`.  
      - **Note:** When using a variable in terraform, the first part, `var.` signifies that you are using a variable.  And the `cidr` represents the specific variable that you are using.  We named this variable, `cidr`.

    - For this step:
      - First uncomment the `cidr_block` argument by deleting the `#` at the beginning of the line
        - **Notice** the line seems to come to life after uncommenting it
      - Then add the appropriate variable `var.cidr`

4. **Review** the `tags` we are adding to the resource.  This is in addition to the **default tags** that we are already adding to all the range resources.


### Challenge 4: Create Your CyberBear Subnets

1. Visit the following Terraform resource documentation for building Subnets, review the docs and learn how to use the resources.

    - [Resource: aws_subnet](https://registry.terraform.io/providers/hashicorp/aws/latest/docs/resources/subnet)

2. Copy the **public** and **private subnet** resource code blocks and paste them under the `vpc` resource in the **NETWORK** section of your range.

  - Your code may get red squiggly lines for everything suggesting errors.  That is ok.  We just need to add the `vpc_id` and `cidr_block` to our resource blocks.  We are going to fix those next. 

        # Creates a PUBLIC subnet within the VPC for publicly available resources
        resource "aws_subnet" "public_subnet" {
          #vpc_id                  =  # References parent VPC
          #cidr_block              =  # Subnet's IP range
          availability_zone       = var.availability_zones[0] # Physical data center location
          map_public_ip_on_launch = true                      # Auto-assigns public IPs to instances -- only use if instance needs to be public, otherwise set to false

          tags = {
            Name = "${local.name_prefix}-public-subnet"
          }
        }

        # Creates a PRIVATE subnet
        resource "aws_subnet" "private_subnet" {
          #vpc_id                  = 
          #cidr_block              = 
          availability_zone       = var.availability_zones[1]
          map_public_ip_on_launch = false

          tags = {
            Name = "${local.name_prefix}-private-subnet"
          }
        }

3. For each subnet, set the `vpc_id` input to associate the subnets with the VPC that we just built in the previous challenge

    - For this step, again start by uncommenting the line.  You want to use the VPC `id` output from the VPC resource you added above.  To do that, set the `vpc_id` input to = `aws_vpc.vpc.id`.  
        - Think of it like this:  
          - *We need to use the **output** from an **aws resource**.* 
          - *Which resource?  --> The **vpc** resource.*  
          - *And what **output* do we want to use from the vpc resource?  --> We want to use the **id**.*
        - Put that all together and you get --> `aws_resource.` `vpc.` `id`

4. Again, for each subnet, set the respective CIDR block

    - Here you want to use the **local variable** that you set for the respective subnet CIDR blocks.  When using **locals**, as they are referred to, you want to preface the input with "local" instead for "var".
    - With that said, your inputs for the subnet CIDR blocks should look like this --> `local.public_sub_cidr_block` and `local.private_sub_cidr_block`, respectively.
    - Again, this reads like this:
      - *You are using a local variable.*
      - *Which variable?*
      - *The respective subnet cidr block variable.*

- **Note** that we are using the availability zone variable we previously added, "us-east-2a" and "us-east-2b", respectively as indicated by `[0]` and `[1]`


### Challenge 5: Add an Internet Gateway

1. Visit the following Terraform resource documentation for building Internet Gateways, review the docs and learn how to use the resources.

    - [Resource: aws_internet_gateway](https://registry.terraform.io/providers/hashicorp/aws/latest/docs/resources/internet_gateway)

2. Copy the **Internet Gateway** code block and paste it into the **NETWORK** section under the subnets

    - **Verify** the VPC association is correct

          # Creates an Internet Gateway to allow VPC traffic to reach the internet
          resource "aws_internet_gateway" "internet_gateway" {
            vpc_id = aws_vpc.vpc.id # Attaches the IG to specified VPC

            tags = {
              Name = "${local.name_prefix}-internet-gateway"
            }
          }


### Challenge 6: Add Route Tables and Route Table Associations for your Subnets

1. Visit the following Terraform resource documentation for building Route Tables, review the docs and learn how to use the resources.

    - [Resource: aws_route_table](https://registry.terraform.io/providers/hashicorp/aws/latest/docs/resources/route_table)
    - [Resource: aws_route_table_association](https://registry.terraform.io/providers/hashicorp/aws/latest/docs/resources/route_table_association)

2. Copy the **route table** and **route table association** code blocks for the public subnet and paste them below the Internet Gateway in the **NETWORK** section

    - **Note:** Since we are not adding any instances to the private subnet of our range, we do not need to build a **NAT Gateway** or add a respective route table for the private subnet.  
        - That said, **IF** you have instances in your private subnet that needs access to the internet, then you would need to create a **NAT Gateway** and add the respective route tables.
    - **Review** the defined `route` for the `public_route_table` is going to the Internet Gateway
    - **Review** the `route_table_id` for `route_table_association` is associating to the public route table

                # Creates a route table for public subnet
                resource "aws_route_table" "public_route_table" {
                  vpc_id = aws_vpc.vpc.id # Associates with VPC

                  route {
                    cidr_block = "0.0.0.0/0"                              # All traffic
                    gateway_id = aws_internet_gateway.internet_gateway.id # Routes through internet gateway
                  }

                  tags = {
                    Name = "${local.name_prefix}-public-route-table"
                  }
                }

                # Associate the public route table with the public subnet
                resource "aws_route_table_association" "public_rta" {
                  subnet_id      = aws_subnet.public_subnet.id           # Subnet to affect
                  route_table_id = aws_route_table.public_route_table.id # Route table to use

                  depends_on = [aws_subnet.public_subnet]
                }


### Challenge 8: Test Build Your CyberBear Range Network

Before you start building CyberBears, it is important to make sure your network is building correctly.

**:tipping_hand_person: PRO TIP:** Make sure you save your code before running commands. :smile:

1. Open a new terminal from the top VS Code menu bar

    - Make sure you are in the working directory where your `main.tf` file exists

2. Run `terraform fmt` to beautify and properly align your code

    - It will still run if you don't format it, but it will be ugly
    - **Side note:** If you save/store code that is not formatted, your peers will think you are lazy or inconsiderate since it will be harder to read
    - Once complete, the terminal will output which files were formatted

3. Run `terraform init` to initialize Terraform providers

    - You will see a new `.terraform` folder created in your VS Code Explorer window for your range.  This contains all the provider and module code you need for building your Terraform code.
    - You will also now see a `.terraform.lock.hcl` file.  This locks in the provide versions, constraints, and hashes.
    - When initialization has completed, you should see the following message in your terminal

        ![Terraform Init Success](/2-building-ranges-aws/images/terraform-init.png)

        ---

4. Run `terraform plan` to test out your code and make sure things are planning **A-OK** --> so far so good  

    - If you get the following error message, it means AWS can not validate your credentials.  You need to configure your AWS profile now or add environment variables.

        ![Terraform Plan Error - No Profile](/2-building-ranges-aws/images/terraform-plan-error-missing-creds.png)

        ---

    - If you would like to configure your AWS profile
      - Install AWS CLI if it is not already installed
      - Run `AWS Configure`
      - Add your `AWS_ACCESS_KEY_ID` and `AWS_SECRET_ACCESS_KEY`

      **OR**

      - Set environment variables *(optional/if needed - if using environment variables you will need to add these every time you open your terminal window)*

          ```
          export AWS_ACCESS_KEY_ID="add-access-key-ID-here"
          export AWS_SECRET_ACCESS_KEY="add-secret-access-key-here"
          ```

    - If your profile is configured and your `terraform plan` runs successfully, you should see the following message in your terminal when the plan completes successfully

        ![Terraform Plan Success](/2-building-ranges-aws/images/terraform-plan.png)

        ---

    - Review your plan

5. If your plan looks good, which it should, run `terraform apply` to deploy your network.   When it asks **"Do you want to perform these actions?"** -- type `yes` -- this is the only acceptable option. Now sit back, relax, and watch the cloud AWSomeness happen right before our eyes! :heart_eyes:

    - You should see "**Apply complete! Resources:** 7 added, 0 changed, 0 destroyed" message in your terminal when the deployment completes successfully.
    - **Notice** a `terraform.tfstate` file was created in your VS Code Explorer window.  This file represent the storage of local state configuration.

        ![Terraform Apply Complete](/2-building-ranges-aws/images/terraform-apply.png)

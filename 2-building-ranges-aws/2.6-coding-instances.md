# 2.6 - Coding EC2 Instances and Security Groups

### Objectives

The objectives of this lesson are to **build, configure, and protect** your **CyberBears** using Terraform.

- Set hostnames and private IP addresses (name and ID your cyberbears :joy:)
- Use Terraform data sources to search for different AWS AMI's
- Create an ssh keypair and store the output on your local machine
- Build a custom security group
- Build an EC2 instance
- Add user-data to configure the instances


## Challenges

### Challenge 2: Use Data Sources to Search For and Use AWS AMIs

1. There are a few different AMI's we want to be able to pull from for future building.  Let's copy the **data** code blocks for each and paste them into the **DATA Sources** section.

    - **Notice** the "most recent" image is being selected
    - **Review** the different filters being used for the respective lookups.  You need to use filters to narrow your search when multiple results may apply.

          # Use Data sources to lookup AWS resources to use in your environment
          data "aws_ami" "ubuntu24" {
            most_recent = true
            owners      = ["099720109477"] // Owner for the vanilla Ubuntu (Canonical)

            filter {
              name   = "name"
              values = ["ubuntu/images/hvm-ssd-gp3/ubuntu-noble-24.04-amd64-server-*"] // Vanilla AWS Ubuntu 24.04 LTS
            }

            filter {
              name   = "virtualization-type"
              values = ["hvm"]
            }
          }

          data "aws_ami" "amazon_linux2023" {
            most_recent = true
            owners      = ["amazon"]

            filter {
              name   = "name"
              values = ["al2023-ami-2023*-x86_64"] // Vanilla AWS Amazon Linux 2023
            }

            filter {
              name   = "architecture"
              values = ["x86_64"]
            }

            filter {
              name   = "virtualization-type"
              values = ["hvm"]
            }
          }

          data "aws_ami" "win2025" {
            most_recent = true
            owners      = ["801119661308"] // Owner for the Vanilla AWS Windows Server

            filter {
              name   = "name"
              values = ["Windows_Server-2025-English-Full-Base-*"] // Vanilla AWS Windows Server 2025
            }

            filter {
              name   = "virtualization-type"
              values = ["hvm"]
            }
          }

### Challenge 4: Create SSH Keys :key: for Your CyberBears 

1. Before we create keys, we need a place to store them.  Let's create a variable for a location to store keys.

    - We will name the variable `secrets_path` and give it a default location of `./secrets`
      - **Note:** The `secrets_path` is a local location that will be used to save the ssh keys that get generated for your range deployment
    - Copy the **secrets path** variable to your range pasting the block in the **VARIABLES** section
    - **:warning: Special Note:** It is **NOT** recommended to create and/store ssh keys like this for production.  Remember, this is a playground.

            variable "secrets_path" {
              description = "The local path where secrets like a VPN client and SSH keys will be written to"
              default     = "./secrets"
              type        = string
            }

2. Copy the **module** code block to create an ssh key pair that you can use to connect to the instance.  Paste code block in the **AWS SSH KEYPAIR** section.

    - **Note:** An `ssh_key_pair` module will be used to generate an ssh public/private key pair that you can use with your range.  A cool side note, the keys you create with the range get destroyed with the range, so they are not long living keys left hanging around.
    - **Review** the inputs we are adding for this resource
    - **(Optional)** Feel free to visit the source of this module noted in the code comments to learn more about it if you would like.  That said, we will spend time later in the course specifically covering using modules to build resources.

            // Source: https://github.com/cloudposse/terraform-aws-key-pair
            module "ssh_key_pair" {
              source                = "git::github.com/cloudposse/terraform-aws-key-pair"
              ssh_public_key_path   = var.secrets_path
              generate_ssh_key      = "true"
              private_key_extension = ".pem"
              public_key_extension  = ".pub"
            }


### Challenge 5: Protect Your CyberBears With A Security Group

1. Visit the following Terraform resource documentation for building Security Groups, review the docs and learn how to use the resources.

    - [Resource: aws_security_group](https://registry.terraform.io/providers/hashicorp/aws/latest/docs/resources/security_group)
    - [Resource: aws_security_group_ingress_rule](https://registry.terraform.io/providers/hashicorp/aws/latest/docs/resources/vpc_security_group_ingress_rule)
    - [Resource: aws_security_group_egress_rule](https://registry.terraform.io/providers/hashicorp/aws/latest/docs/resources/vpc_security_group_egress_rule)

2. Copy the `aws_security_group` and the corresponding rules resource code blocks and paste in the **SECURITY** section 

        # Creates security group and ingress/egress rules (firewall) for instances
        resource "aws_security_group" "cyberbear_sg" {
          name        = "${local.name_prefix}-security-group"
          # Add simple description for the Security Group
          description = "Allow SSH, HTTP, and HTTPS from the world"
          vpc_id      = aws_vpc.vpc.id
        }

        resource "aws_vpc_security_group_ingress_rule" "allow_ssh" {
          description       = "Allow SSH from anywhere"
          security_group_id = aws_security_group.cyberbear_sg.id
          from_port         = 
          to_port           = 
          ip_protocol       = "tcp" 
          cidr_ipv4         = "0.0.0.0/0" # Source IPs (any) - This is the same as global allow and should only be used with ports 80 & 443
          # Security Group ingress CIDR blocks should be restricted to the specific IPs required for the service
          # Only setting ssh global allow for playground purposes; NEVER set global allow ssh in production

          tags = {
            Name = "allow-ssh"
          }
        }

        resource "aws_vpc_security_group_ingress_rule" "allow_http" {
          description       = "Allow HTTP from anywhere"
          security_group_id = aws_security_group.cyberbear_sg.id
          from_port         = 
          to_port           = 
          ip_protocol       = "tcp" 
          cidr_ipv4         = "0.0.0.0/0" # Source IPs (any) - This is the same as global allow and should only be used with ports 80 & 443
          # Security Group ingress CIDR blocks should be restricted to the specific IPs required for the service

          tags = {
            Name = "allow-http"
          }
        }

        resource "aws_vpc_security_group_ingress_rule" "allow_https" {
          description       = "Allow HTTPS from anywhere"
          security_group_id = aws_security_group.cyberbear_sg.id
          from_port         = 
          to_port           = 
          ip_protocol       = "tcp" 
          cidr_ipv4         = "0.0.0.0/0" # Source IPs (any) - This is the same as global allow and should only be used with ports 80 & 443
          # Security Group ingress CIDR blocks should be restricted to the specific IPs required for the service

          tags = {
            Name = "allow-https"
          }
        }

        resource "aws_vpc_security_group_egress_rule" "allow_all" {
          description       = "Allow all outbound traffic"
          security_group_id = aws_security_group.cyberbear_sg.id
          ip_protocol       = "-1"        # semantically equivalent to all ports
          cidr_ipv4         = "0.0.0.0/0" # All destinations
          # In production, egress rules should be restricted to ports/protocols needed for specific business use case

          tags = {
            Name = "allow-all-egress"
          }
        }

3. Add the `from_port` and `to_port` for the three respective ingress rules based on the respective rule descriptions

    - **Review** the ports and IP addresses we are allowing in this Security Group
      - `ip_protocol = "-1"` semantically equivalent to all ports
      - `cidr_ipv4   = "0.0.0.0/0"` represents global allow
    - **Note:** Each rule requires a unique resource


### Challenge 7: Configure Your First CyberBear -- Big Bear

1. Visit the following Terraform resource documentation for building Security Groups, review the docs and learn how to use the resources.

    - [Resource: aws_instance](https://registry.terraform.io/providers/hashicorp/aws/latest/docs/resources/instancep)


2. Copy the code block for **Big Bear** and paste in the **CYBER BEARS** section

        #######################################
        # Big Bear
        #######################################
        # Creates EC2 instance
        resource "aws_instance" "big_bear" {
          ami                         =  # Amazon Machine Image
          instance_type               =  # Server size (CPU/memory)
          subnet_id                   =  # Network placement
          vpc_security_group_ids      = [] # Firewall rules.  Square brackets are used for this input because it takes a list
          private_ip                  =  # Private IP assignment
          associate_public_ip_address = true # Auto-assigns public IPs to instances -- only use if instance needs to be public, otherwise set to false
          #ebs_optimized               = true # Optimize ebs for best performance
          #monitoring                  = true  # Use detailed monitoring in production

          # Forces IMDSv2 (required for security)
          #metadata_options {
          #  http_tokens = "required"
          #}

          # Encrypts the root block (required for security)
          #root_block_device {
          #  encrypted = true
          #}

          # Pass inline user-date script directly
          user_data = <<-EOF
            #!/bin/bash
            sudo yum update -y
            sudo yum install httpd -y
            sudo systemctl start httpd
            sudo systemctl enable httpd
            cd /var/www/html
            echo "<html><h1>Hello Cloud Rangers. Welcome to the ${local.big_bear_hostname} webpage.</h1></html>" > index.html
            EOF


          tags = {
            Name = "${local.name_prefix}-${local.big_bear_hostname}"
          }

          depends_on = [aws_subnet.public_subnet]
        }


3. Set the following resource inputs to complete the requirements needed for building `big_bear`
    - AMI = use the data lookup for Amazon Linux 2023.  It needs the ID for the `ami`, so do not forget to add the `.id` at the end
    - Instance Type = use the variable for Linux servers
    - Subnet = use the output `id` for the `public_subnet`
    - Security Group = use the output `id` for the `aws_security_group`
    - Private IP = use the local variable for the private ip
    - Associate Public IP address = true

4. **Note:** The user-data script is added directly to the instance resource block to configure the instance during launch.  Scripts can be added inline or as a separate script outside of the `.tf` file.
